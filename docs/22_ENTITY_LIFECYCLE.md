## Почему это системное действие

Удаление объекта — часть закона игры об идентичности и представлении, потенциальный путь к мета-секретам. Оно **не имеет права удалять реальные файлы пользователя**. Исчезновение 3D-тела не означает удаления личности Луны или профиля игрока. На этой стадии **PLAYER_AVATAR защищён**: Luna не является обычной HackableEntity; полноценное удаление/смена её тела будет реализовано только с AvatarBindingService и восстановлением.

## Реализованные операции

- `EntityLifecycleService.capture(id)` — снимок данных существующей Entity: ID, исходная категория, позиция, все редактируемые параметры, явные роли и теги; также сохраняются происхождение копии и магический рецепт там, где они применимы.
- `EntityLifecycleService.validate_blueprint(data)` — белый список категорий/ID/типов/параметров, запрещён ID игрока. Непроверенные параметры или некорректные магические рецепты отвергаются до создания Node.
- `EntityLifecycleService.restore_entity(snapshot)` — создать новый Node через один фабричный путь, зарегистрировать прежний ID, восстановить параметры/теги/роли и данные, связанным с удалением. ID остаётся стабильным; Node-ссылка всегда новая.
- `EntityLifecycleService.delete_entity(id)` — исключить из WorldRegistry, отключить физику/коллизии, запланировать освобождение Node, захватить только связанные с ним социальные связи и состояния для Undo.
- `EntityLifecycleService.unload_entity(id)` — техническое удаление при загрузке снимка мира без создания нового игрового факта «удалено».
- `CommandProcessor.execute_entity_delete(...)` и `execute_entity_create(...)` — команды с аудитом, автором и источником, Undo/Redo. Copy теперь пользуется этим маршрутом, а не отдельно вызывает фабрику и забывает команду.
- `Main` передаёт события `entity.created` / `entity.deleted` в EventBus. Внутренняя схема использует стабильные строковые ID.

## Ссылки и отношения

- Соседние сущности не хранят вечных прямых ссылок на удалённый Node: WorldRegistry возвращает `null` для отсутствующего ID, поиск целей игнорирует удалённые объекты.
- `RelationshipService.take_entity_links` захватывает только входящие и исходящие отношения этого ID, удаляет их из активного графа. Undo восстанавливает эти рёбра без перезаписи отношений между **другими** сущностями.
- Стихийные статусы и социальные оповещения, связанные с удалённым ID, временно убираются; Undo восстанавливает их при наличии валидных участников. RuleEngine сохраняет описания правил с owner_id, но когда owner отсутствует, не запускает их.
- Копия не наследует исходные отношения/временные статусы. Её `copy_origin` остаётся текстовым ID предка, даже если предок удалён.

## Сохранения и совместимость

- `WorldRegistry.retire_entity(id)` создаёт надгробную запись (*tombstone*), а простой `unregister_entity` предназначен для системной выгрузки и тестового teardown. Это различие исключает случайную запись удалений при очистке сцены.
- `SaveService.snapshot` теперь добавляет `deleted_entities: ["fridge_001", ...]` (макс. 128). Данные не содержат Node, исполняемых скриптов или ссылок на системные файлы.
- `SaveService.apply_snapshot` проверяет типы и коллизии ID: одна запись не может одновременно находиться в `entities` и `deleted_entities`; `luna` никогда не удаляется.
- При загрузке существующие удалённые оригиналы убираются, а если снимок содержит оригинал, ранее удалённый в текущей сессии, фабрика восстанавливает исходный ID и тип.
- Старые снимки без `deleted_entities` остаются действительными, отсутствие этого поля означает отсутствие записанных удалений.
- Удаление временно созданных магией/дублированием объектов учитывается точно так же. Нумерация новых экземпляров пропускает удалённые ID, чтобы не подменить прежнюю идентичность.
- Внутренняя история Undo **не сохраняется** между сессиями: игрок может восстановить мир через ранее сделанный checkpoint, если такая запись осталась. При выходе из сцены временная история и callback-подписки освобождаются.

## Ограничения 0.21 и долги

1. `SPAWN / DELETE` пока отдельные типизированные команды в CommandProcessor, а не произвольные операции внутри атомарного многошагового EffectEngine. Чтобы заклинание, ловушка и правило могли менять жизненный цикл, сначала расширить транзакции с валидацией и откатом нескольких сущностей.
2. Хранение удалённых объектов в памяти не предполагается; Undo воссоздаёт новый Node из данных, поэтому уникальные неописанные свойства ассетов необходимо постепенно выносить в компоненты.
3. Динамические ссылки эффектов и внешние условные события пока не являются универсальным графом ссылок; новый ReferenceService/TargetResolver должен использовать только стабильные ID.
4. Пока нет общей команды физического удаления самого PLAYER_AVATAR, сценарного мира, предмета в инвентаре или двери. Это потребует отдельного контракта, включая безопасное восстановление.
5. UI удаления у редактируемого объекта демонстрационный; в одном ряду находятся кнопки COPY DELETE DONE без других слов, кнопки Undo/Redo в нём скрыты намеренно. Позже игрок получит понятный доступ к восстановлению, не превращающий UI в полноценный SDK.

### Продолжение: 0.22

Typed lifecycle операции теперь могут завершать общую транзакцию после эффектов на других сущностях. Это важный, но ограниченный вариант атомарности: только один lifecycle шаг в конце, не более 12 эффектов; создание и редактирование новой Entity в одной цепочке пока отсутствует. См.
