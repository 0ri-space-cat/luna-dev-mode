# LUNA: DEV MODE — V3. Системная магия, hack-and-slash, еда, напитки, двери и комбинации

> **10.11.2026 · Рабочая целевая спецификация.** Этот файл различает **[УЖЕ ЕСТЬ В GODOT]**, **[ПЕРВАЯ КОДОВАЯ ЗАГОТОВКА V3]** и **[ЕЩЁ СПРОЕКТИРОВАТЬ/РЕАЛИЗОВАТЬ]**. Не путать игровое намерение с кодовой готовностью. Пользователь выбрал: полноценные взаимодействия в духе Magic Circle и хорошего hack-and-slash, но мир должен оставаться маленькой многоуровневой Этернией, которую можно исследовать без обязательных боёв и без перков/XP.

## 0. Основной принцип системного дизайна

Игрок должен иметь возможность сказать: **«Я знаю, как работают эти две вещи. Интересно, что произойдёт, если соединить?»** И получить честный, узнаваемый результат.

Рабочая цепочка каждого действия:

```text
INPUT (attack / wand / spell / food / door / AI / NPC tool)
  -> TARGET RESOLVER (actual Entity IDs, positions, roles, tags)
  -> CAPABILITY & ACCESS (tool held? skill present? location editable?)
  -> VALIDATE (type, range, cost, affected targets, resistances)
  -> PREVIEW SHADOW STATE (all changes and side effects)
  -> ATOMIC COMMIT / UNDO GROUP
  -> DERIVED REACTIONS (fire + wet, mood + social, physics + size ...)
  -> EVENT BUS (NPC awareness, dialogue, quests, persistence)
  -> VISUAL / AUDIO REPRESENTATION (never the authoritative truth)
```

В существующем прототипе **[УЖЕ ЕСТЬ]** ParameterRegistry, CommandProcessor, EffectEngine, SpellService, ArcaneGrammar, ElementalStatusService, SurfaceFieldService, RelationshipService, RuleEngine, InteractionService, SaveService, inventory and partial portable abilities. **[ЗАГОТОВКА V3]** добавлены `ConsumableService`, `WorldAccessService`, `AbilityBankService` и типизированные `CONSUMABLE`, `DOOR_LINK`, `ABILITY_BANK`, `access_level`, `portions`; большинство операций ещё **не имеют UI/сцен/анимаций**. Полноценного динамического комбинированного бойца и временных пищевых статусов пока нет.

## 1. Пять независимых частей сущности

1. **Identity** — `ENTITY_ID`, имя, происхождение, память, связи. Не меняются случайно при выборе новой модельки.
2. **Base properties** — здоровье, максимумы, скорость, размер, материал, настроение, радиус чувств, адрес двери, проводимость, температура. Типизированный реестр значений.
3. **Abilities** — функциональные модули `WALK`, `FLY`, `SWIM`, `FIRE_BREATH`, `GLOW`, `OPEN_DOORS`, `ELECTRIC_AURA`. У модуля есть реальный носитель и физический эффект; при извлечении модуль исчезает у донора.
4. **Transient effects** — `WET`, `BURN`, `FROZEN`, `CHILL`, `SHOCK`, `HASTE`, `SLOW`, `STICKY`, `BUBBLE_SHIELD`, `MOOD_BOOST`. У каждого источник, длительность, сила, правило сложения, возможность очистить. В текущем коде реализованы не все; полный перечень — будущая спецификация.
5. **Presentation & observer** — спрайт/слои/anchors, коллизия, видимость, прямой взгляд героя, поле камеры, специальные восприятия. То, что видно в кадре, может не совпадать с живой истинной сущностью.

**Системный инвариант:** 3D-ноды нынешнего прототипа — адаптеры/graybox. Canon V3 целиком 2D. В ядре операций нет требований к `Node3D`; существующий runtime ещё использует `Node3D` в пространственных сервисах и его предстоит заменить абстракцией `WorldPosition/SpatialQuery`. Не копировать эту зависимость в новые механики.

## 2. Набор редактируемых параметров: целевые семьи

| Семья | Примеры полей | Что физически меняется | При каком доступе |
|---|---|---|---|
| Жизнь и ресурс | `HEALTH`, `MAX_HEALTH`, `MANA`, `STAMINA`, `IS_ALIVE` | Реальная выживаемость, цена заклинаний, поведение смерти | USER обычно |
| Движение | `MOVE_SPEED`, `ACCELERATION`, `JUMP_FORCE`, `GRAVITY_VECTOR` | Скорость, траектория, падение, толчки | USER/редкий артефакт |
| Тело | `SCALE`, `MASS`, `COLLISION_ENABLED`, `MATERIAL`, `WETNESS`, `TEMPERATURE` | Попадание, проходимость, элементы, плавучесть | USER/OPERATOR |
| Поведение | `BEHAVIOR_MODE`, `AI_ENABLED`, `FOLLOW_TARGET`, `AVOID_TARGET`, `SENSE_RANGE` | Самостоятельные реакции живых сущностей | USER; глубокое дерево через `SCAN_DEPTH` |
| Отношения | `FRIEND`, `AFRAID`, `OWNER`, `TRUST`, `MOOD_STATE`, `MOOD_INTENSITY` | Социальное поведение, ауры, скрытые последствия | USER/различное зрение |
| Еда и зелья | `PORTIONS`, `USE_EFFECTS`, `DELIVERY_MODE`, `EFFECT_DURATION` | Кого и сколько действует выпитое/брошенное | USER, безопасность валидатора |
| Двери и мир | `TARGET_LOCATION`, `LOCATION_EXISTS`, `LOCATION_CLASS` | Реальные адресные переходы | USER для обычных; ADMIN для защищённых |
| Наблюдение | `VISIBLE`, `GAZE_REACTIVE`, `CAMERA_FOLLOW_TARGET`, `CAMERA_LOCKED` | Внешний вид и физика особых мостов | Разные уровни: предмет/спецдоступ |
| Система | `ACCESS_LEVEL`, `SCAN_DEPTH`, `CHARACTER`, `GAME_FRAME` | Кто может редактировать системные объекты | Физическая копия палочки, доверенный инструмент, знание |

Строки — **словарь целевого дизайна**. Не утверждать, что каждая из них зарегистрирована и работает в текущем `ParameterRegistry`. В частности `MANA`, `STAMINA`, `MASS`, `MOOD_STATE`, `TARGET_LOCATION`, `CAMERA_LOCKED` пока нельзя считать готовыми только потому, что они описаны.

## 3. Боевое взаимодействие в режиме экшен-RPG

### Обычный бой и магический бой не должны конкурировать за одну кнопку

**Вне редактора — real-time hack-and-slash**: рывок, прыжок, уклонение, базовый удар/удар палочкой, прицельное заклинание, заряженное заклинание, контекстное взаимодействие, смена активного спелла, поднятие/бросок физического предмета. Всё с правдоподобными hitboxes, инерцией и телеграфированными атаками. Герои/звери имеют короткие реактивные анимации; мир не превращается в обязательную арену с бесконечным гриндом.

**При вызове редактора — временная пауза игрового мира** и видимая цель. Игрок может менять доступные параметры, комбинировать эффекты и сохранить/отменить. UI остается русским, технические имена в `CAPS`. После подтверждения изменения взаимодействуют с продолжающейся симуляцией.

**Заклинание создаёт настоящую сущность эффекта**, если у него физическое проявление: снаряд, лужу, огонь, пузырь, ледяную дорожку, электрическое облако. Её можно обнаружить, выбрать, изменить размер/свойства и направить на других. Снаряд в полёте при подходящем `SCAN_DEPTH` — допустимая системная цель, а не декоративная текстура.

### Предлагаемый простой ритм боя

1. **Подготовка**: игрок видит поведение противника и поверхность.
2. **Реакция**: прыжок/уклонение/блок/бросок или простое заклинание.
3. **Контакт**: единый `HitEvent` с инициатором, целью, материалом, направлением, радиусом и элементом.
4. **Последствия**: `HEALTH`, `KNOCKBACK`, статусы, физические эффекты, эмоции/агрессия свидетелей.
5. **Комбинация**: следующее действие считывает остаток предыдущего (вода + молния, пар + ветер, лёд + огонь).
6. **Восстановление**: после схватки мир живёт дальше; поведение противников изменяется без автоматического респавна всех по скрипту, исправление вреда возможно понятными инструментами.

**Проверка свободы:** в основных сюжетных загадках с противниками нужны также небоевые исходы — уйти через дверь, спрятаться, отвлечь предметом, поменять отношение, снизить агрессию, сделать проход, заморозить поверхность, отвлечь взгляд. Бой — часть песочницы, не проверка уровня прокачки.

## 4. Универсальные элементы и реакции

Материал имеет реальные свойства `FLAMMABLE`, `CONDUCTIVE`, `ABSORBENT`, `FRAGILE`, `SLIPPERY` и т.п. Сила элементов зависит от поверхности, мокроты, физического размера, активных статусов. Реакции вычисляются **одной таблицей**, а не вручную в каждом уровне.

| Комбинация | Физический результат | Сценарная польза | Код сейчас |
|---|---|---|---|
| `FIRE + ICE` | Тает лёд, возникает пар | Освободить проход, закрыть линию зрения | **Частично есть** |
| `FIRE + WET` | Тушение, испарение, пар | Безопасно пройти огненный коридор | **Частично есть** |
| `FIRE + WOOD` | Воспламенение с временем горения | Поджечь деревянную преграду, отвлечь | **Частично есть** |
| `WET + STORM` | Проводящий разряд через соседей/лужу | Активировать механизм с другого берега | **Частично есть; уточнить формулу** |
| `FROST + WATER` | Временная ледяная поверхность | Пересечь ручей, построить ступеньку | **Частично есть** |
| `HEAT + OIL` | Горение/скользящая опасная дорожка | Два разных способа пройти коридор | **Нужно** |
| `SHRINK + MASS` | Меняется размер и проходимость, вес — отдельно | Мия переносит блок через решётку | **Размер есть; полная масса — нужно** |
| `FLY + HEAVY` | Скорость/подъём зависит от массы/тяги | Летучий холодильник и бочки | **Нужно реальное движение** |
| `FIRE + WIND` | Направленный конус распространения/пар | Разогнать туман или выпустить дым | **Нужно** |
| `LIGHT + HIDDEN_INSECT` | Существо тянется к свету, даёт косвенную улику | Toффи и скрытая фауна | **Нужно** |
| `GLOW + INK_SLIME` | Слайм оставляет видимый след на поверхности | Нащупать невидимую дорожку | **Нужно** |
| `MOOD_CALM + HOSTILE` | Аффект меняется, но отношения/память сохраняются | Прекратить конфликт, не стерев причину | **Социальная база есть; нужно взаимодействие** |
| `WANDER + FOLLOW_TARGET` | Реальный приоритет AI определяет итог движения | Холодильник идёт по заданному маршруту | **База поведения есть; уточнить приоритеты** |
| `POTION_RESIDUE + RAIN` | Эффект вновь переносится водой | Сухая лужа возвращает действие | **Нужно** |
| `INVISIBILITY + COLLISION` | Не видно, но мешает проходу | Невидимый мост | **Нужно отдельное наблюдение/коллизия** |
| `GAZE_REACTIVE + CAMERA_OBSERVATION` | Разные независимые сенсоры, не взаимозаменяемые | Застенчивый и внекадровый мосты | **Нужно** |

**Очередность реакций:** сначала проверка физической возможности, затем первичный эффект, затем ограниченная цепь производных реакций (максимум 8 по одному корню события), затем NPC-свидетели и рендер. При откате обязаны вернуться **все** побочные эффекты; эффекты, которые не поддерживают атомарный откат, нельзя без предупреждения включать в общую команду. Избегать рекурсивного поджигания бесконечной цепью и длительного повторного использования одного и того же `HitEvent`.

## 5. Еда и напитки — системная магия в быту

В Этернии почти любая еда и напиток с подходящей физической категорией может быть `Entity`: яблоко, чай, кофе, лимонад, суп, булочка, пирог, желе, конфета, энергетический сок, алхимический чай. У съедобного объекта есть **порции**, **рецепт**, **способ доставки**, потенциальная температура/состав/вкус, владелец, доступность/радиус. Всё это реальные поля, а не «список зельев в коде».

**Способы доставки**:
- `CONSUMER`: съевший/выпивший получает эффект (Луна, NPC или зверушка).
- `TARGET`: выбранное существо получает эффект через подачу/передачу — необходимы близость и реальный предмет; социальный AI может отказаться.
- `SPLASH`: содержимое разбрызгивается и действует на ограниченный набор близких живых получателей, при этом учитывает мокроту/материал/сопротивление.
- **Позднее** `POUR`: состав переливают в другую ёмкость или на пол, сохраняя носитель/разбавление и остатки. В первой V3-заготовке кодом не поддержан.

### Простые «neat» рецепты для первой песочницы

| Предмет | Что игрок взламывает | Комический / физический результат | Статус |
|---|---|---|---|
| Яблоко восстановления | `USE_EFFECTS = ADD HEALTH 15` | Луна или её друг исцеляется, яблоко теряет порцию | **V3-заготовка** |
| Чай бодрости | `USE_EFFECTS = MULTIPLY MOVE_SPEED 1.5` | Выпивший ускоряется; чашка без рецепта не бегает сама | **V3-заготовка (пока постоянное изменение)** |
| Лимонад вечеринок | `DELIVERY = SPLASH`; `ADD MOVE_SPEED` | Несколько существ начинают бегать по комнате | **V3-заготовка (мгновенные параметры)** |
| Смузи великана | `ADD SCALE 0.5` | Луна не помещается в дверь, может нажать большую кнопку | **V3-заготовка (пока постоянный размер)** |
| Чай спокойствия | `MOOD_STATE = CALM` на 20 с | Нервный куст расслабляется, но его симпатии не исчезают | **Нужно статус/эмоции** |
| Суп огнедышащего холодильника | `GRANT_TEMP_ABILITY = FIRE_BREATH` | Выпивший холодильник изрыгает огонь; внешность не меняется | **Нужно временные способности** |
| Электролимонад | `APPLY_STATUS = SHOCK_AURA` | Мокрый герой по ошибке проводит заряд через лужу | **Нужно статусы и проводимость** |
| Пирожное-пружинка | `JUMP_FORCE` + `BOUNCY` | Луна прыгает как слайм и случайно бьётся о потолок | **Нужно физика прыжка** |
| Чай-невидимка | `OPACITY = 0` / `VISIBLE = FALSE` | Луна невидима, но её шаги и коллайдер остаются | **Нужно видимость/наблюдение** |
| Суп эхоподражания | `ECHO_MOVE` на 15 с | Повторяет последнее движение с задержкой, даёт улику о временных следах | **Нужно** |
| Пирог дружбы | `MOOD_BOOST` + `SMILE` | Герой становится счастливее, но принудительная дружба не появляется | **Нужно** |
| Капучино полёта | `TEMP_ABILITY = FLY`, 10 с | Даже бочка летает, если её научили пить | **Нужно** |
| Конфета-лёд | `FROST_RESIST` на 30 с | Луна проходит по ледяной дорожке без замедления | **Нужно** |
| Слаймовое желе | `MATERIAL = SLIME` на время | Герой проскальзывает в узкое пространство | **Нужно физические материалы** |
| Шипучка тишины | `NOISE_FACTOR = 0.1` | Игрок может пройти мимо чувствительного существа | **Нужно восприятие AI** |

**Ключевой контраст:** редактировать `MOVE_SPEED` самой бутылки — влияет на *бутылку* (если она оживлена и может перемещаться). Записать `ADD MOVE_SPEED` в её `USE_EFFECTS` — влияет на *получателя*. Эта разница должна быть наблюдаема в буфете U-03 с первого опыта.

### Опасные, но обратимые эксперименты

- Изменить `IS_ALIVE` у еды: пирожное может убежать от покупателя; пока его не съели, порции сохраняются.
- Добавить `FOLLOW` чашке, затем `SPLASH`: напиток самостоятельно бегает за NPC и может обрызгать нескольких — когда появится collision event `ON_TOUCH`.
- `COLOR` напитка можно менять без изменения его реального эффекта; это наглядный урок «внешность ≠ свойства».
- `MATERIAL` чашки на металл и `WET` → она начинает проводить разряды, но чай внутри остаётся самостоятельным предметом-носителем.
- Удалить объект чашки после выпивания: уже действующий временный эффект должен остаться, пока не закончится или не будет очищен.
- Дать гигантскому невидимому скату еду через автоматический маршрут: меняется его желание/маршрут, но сам скат не появляется «только в момент квеста».

### Технический контракт исполнения напитка

1. Найти реальную еду/напиток; проверить, что предмет не у другого владельца и рядом.
2. Найти `CONSUMABLE` и `PORTIONS > 0`, собрать эффективный рецепт (стандартный + взломанные изменения).
3. Определить **проверяемый** набор получателей `CONSUMER/TARGET/SPLASH`. Не допускать бесконечный target fanout.
4. Рассчитать стоимость, сопротивления, число оставшихся порций, побочные реакции в теневом состоянии.
5. **Один атомарный commit**: получатели получают эффекты и `PORTIONS` уменьшается.
6. Только после успеха — звук, крошки, анимация питья и реакции NPC. При ошибке порция остаётся.
7. Временные эффекты идут в `StatusRuntime`, имеют собственный `effect_instance_id`, источник, длительность, `tick` и раздельный `cleanse`. Постоянное редактирование свойства через пищу разрешается только для явной особой категории рецепта и должно быть указано игроку. **Этот слой ещё предстоит реализовать**, первая V3-заготовка меняет значения непосредственно.

## 6. Банк способностей и перенос: полноценная «магическая химия»

**[УЖЕ ЕСТЬ]** `ABILITY_SET` + `AbilityService` дают базовый список активируемых эффектов. **[V3-ЗАГОТОВКА]** `AbilityBankService` реально извлекает модуль из существа в физически принадлежащий игроку компонент `ABILITY_BANK` и вводит его в другую сущность одной отменяемой транзакцией.

**Как это должно выглядеть:**
- выбрать донора (овечка), открыть «Способности»;
- увидеть `WALK`; извлечь → овечка временно не ходит и не теряет `ENTITY_ID`;
- в Банке одна реальная единица `WALK`; скопировать её магически нельзя без самостоятельного свойства дублирования;
- выбрать холодильник; поставить `WALK` → холодильник начинает ходить, проигрывается подходящая 2D-анимация;
- `UNDO` возвращает способность владельцу или возвращает её в Банк в зависимости от последней операции;
- `FLY` на бочку работает даже без крыльев. Если крылья нарисованы, но `FLY` нет — бочка не летает.

**Не выдавать перенос модуля за готовое движение** до реализации `AbilityRuntime`, который связывает `WALK/FLY` с физическим актором и 2D-визуальными якорями. Первая V3-заготовка гарантирует **атомарность записи**, а не полный motion controller.

### Комбинации способности + свойства

| Сборка игрока | Результат | Неочевидная тонкость |
|---|---|---|
| `FLY` + увеличенный `MASS` | Тяжёлый предмет набирает высоту медленно | Функция и физическое ограничение сосуществуют |
| `WALK` + `IS_ALIVE = FALSE` | Неживой предмет не принимает самостоятельные решения, если runtime требует жизнь для автономии | Отдельная возможность командовать через автоматическое правило |
| `FOLLOW` + `AFRAID` | Хочет уйти, но внешнее поведение преследует цель | Лея объясняет социальное противоречие |
| `GLOW` + `VISIBLE = FALSE` | По настройкам свет может выдавать невидимое тело | Свет и модель не обязаны совпадать |
| `WATER_BREATH` + `FIRE_BREATH` | Пар при попытке одновременного выдоха (если оба активны) | Реакции элементов универсальны |
| `MAGNETIC` + `SCALE` | Изменяется зона притяжения по типизированной формуле | Не привязывать эффект к форме спрайта |

## 7. Двери, адреса и системный доступ

### Четыре уровня прав (механика предмета, не RPG level)

| Уровень | Название | Что позволяет |
|---|---|---|
| `0 USER` | обычная взломанная палочка | Изменять доступные параметры, `TARGET_LOCATION` публичных дверей, простые рецепты |
| `1 OPERATOR` | расширенный инструмент | Продвинутые служебные маршруты/параметры в пределах локальной зоны |
| `2 ADMIN` | например, подлинная консоль Юки, если закреплено сценарно | Редактировать защищённые сервисные адреса, которые нельзя менять обычной палочкой |
| `3 DEVELOPER` | высший уровень палочки/настоящий системный доступ | Системные переходы, расширенные параметры камеры/рамки, `GAME_FRAME` |

**Ключевые разделения:**
- `KNOWN_ADDRESS`: игрок знает буквенный адрес, этот факт сам по себе **не даёт разрешения менять защищённую дверь**.
- `ACCESS_LEVEL`: физическое свойство конкретного инструмента; не XP, не награда за главу.
- **Редактирование адреса** требует права на целевой адрес. Базовая палочка уже может перенаправить обычную дверь в `ELF_HOUSE_04`, если адрес на данном уровне считается публичным/доступным.
- **Открытие уже настроенной двери** обычно разрешено обычному персонажу, даже если он не мог бы сам перепрограммировать её на защищённую системную область. Иные материальные препятствия (замок, физическая печать) существуют отдельно и должны быть честно показаны.
- `UNKNOWN_LOCATION` означает адрес отсутствует в каталоге; `LOCATION_FORBIDDEN` означает адрес известен/валиден, но прав не хватает. Понятная разница — подсказка, а не скрытый квестовый флаг.
- **Юкина системная роль** не должна определяться редактируемым `ROLE=ADMIN` у персонажа. Подлинное право инструмента/консоли устанавливается доверенным контекстом игры. Игрок не получает права лишь потому, что вписал слово ADMIN в доступный текст.
- **Озеро Дубликатов**: палочка, дублированная физически, может взломать оригинал и повысить его уровень. При этом оригинал не может просто поднять собственный `ACCESS_LEVEL` через обычное саморедактирование.

**[ЗАГОТОВКА V3]** `WorldAccessService` хранит реестр валидных адресов, проверяет диапазон доступа, физический доступ к принадлежащей палочке и отличает редактирование двери от её использования. Сейчас метод `resolve` **только возвращает проверенный `region_id/entry_id`**, сменой уровня ещё не управляет. Требуются `WorldManager2D`, регистрация всех адресов, входные якоря, переходы с сохранением, rollback и обновление карты.

### Важные тестовые случаи

1. `ET_MARKET` с `required_access=0`: базовая палочка меняет дверь.
2. `VOID_DEEP` с `required_access=3`: базовая палочка → `LOCATION_FORBIDDEN`.
3. Подделать `ADMIN` через редактируемый `ROLE` → **не получить** право.
4. Взломать свою палочку её же интерфейсом → **не получить** `ACCESS_LEVEL=3`.
5. Реальная копия палочки с `copy_origin` и физической принадлежностью игроку → может изменить оригинал.
6. Войти в уже перенаправленную дверь с обычным инструментом → разрешено, если `DOOR_LINK.enabled` и пространственные условия соблюдены.
7. Неверный адрес → остаёмся на месте; никаких загрузок произвольных файлов или обращения к ОС.
8. Переход в системную область никогда не зависит от флага «завершил все побочные задания».

## 8. Неожиданные взломы, которые должны работать между уровнями

| Ситуация | Исходный закон | Смелое применение | Урок/связь |
|---|---|---|---|
| Больная зверушка не подходит к лекарству | Изменяемый рецепт | Залить лекарство в другую еду или поднести через `TARGET` | Лея + Мия |
| Огромный холодильник не проходит в маленькую дверь | `SCALE`, `TARGET_LOCATION` | Уменьшить, перелететь, телепортировать другую дверь | Луна + Юки |
| Невидимый мост плохо виден | Невидимость не убирает коллизию | Бросить чернильного слайма, поджечь пар над мостом | Юки + Мия + Тоффи |
| Охранник не пускает на башню | AI+отношения+адрес | Успокоить, обойти, подменить target двери | Лея + Луна |
| Стена закрывает предмет | Коллизия отдельно от модели | Изменить размер, нарисовать другой модуль, наложить `FLY` | Ори + Луна |
| После питья у NPC появляется способность | `USE_EFFECTS` + `ABILITY_SET` | Сварить еду с переносом временной способности | Мия + Луна |
| В кафе кто-то сидит на пустом стуле | Представление ≠ Entity | Сканировать связи стула и старый адрес комнаты | Лея + Они |
| Нора исчезает, когда на неё смотрят | `DIRECT_GAZE` | Закрыть глаза, направить следящего питомца | Тоффи |
| Мост остаётся несуществующим с закрытыми глазами | `CAMERA_VIEW` отдельно от глаз | Отвязать камеру, выйти за её рамку | Зеркало + системный взлом |
| Дверь показывает запретный адрес | `ACCESS_LEVEL` у инструмента | Добыть копию палочки и усилить оригинал | Озеро + Юки |
| Живой предмет спасает NPC | AI, способности и физика | Обучить стул ходить и направить его к человеку | Луна + Ори |
| Призма показывает изнанку без рук | Восприятие независимо от палочки в руке | Исследовать скрытую площадку с другим инструментом | Общая изнанка |

## 9. Встраивание в сохранения и тестирование

Все эффекты должны различать **постоянную правку**, **временную модификацию**, **системное разрешение**, **сюжетный факт** и **представление камеры**. Не складывать их в одно поле `level` или `unlocks`.

Минимальный формат данных:
```json
{
  "entity_id": "drink_mint_001",
  "category": "drink",
  "properties": {"portions": 2, "color": "MINT"},
  "components": {
    "CONSUMABLE": {
      "delivery": "CONSUMER",
      "radius": 2.5,
      "max_targets": 3,
      "effects": [{"operation": "ADD", "parameter_id": "health", "value": 15}]
    }
  },
  "effects_active": [],
  "events": [{"type": "entity.consumed", "target_id": "luna"}]
}
```
Это **проектный формат примера**, не прямой файл, который нынешний `SaveService` принимает без адаптации. Код V3 сохраняет компоненты через существующий `ComponentRegistry`, однако пока не поддерживает обобщённый `effects_active` для всех типов статусов и сохранение всех новых сюжетных подсистем.

**Обязательный кодовый «definition of done»:** операция прошла type validation; отработала через один путь; атомарна при нескольких получателях; правильно откатилась; эффект у NPC и у Луны одинаково обоснован; повторные правила ограничены; сохранение/загрузка сохраняет Entity ID/порции/компоненты; UI показывает обратную связь; при миграции 2D авторитетным остаётся модель, а не спрайт.

## 10. Очередь реализации без готовых ассетов

**M1 — завершить ядро взаимодействий (сейчас V3-заготовка):** формальные tiers, валидные адреса и защищённые системные поля; съедобные предметы с мгновенными рецептами; реальный Банк способностей; Unit/CI проверки сохранения и Undo. Подключить к существующему graybox; не делать финальный UI.

**M2 — общий stat/status runtime:** временные модификаторы, `MANA`, `STAMINA`, `MAX_HEALTH`, сроки, источник/сила эффектов, складывание/очистка, реакции сопротивлений и оконных состояний. Отдельно уточнить, что сейчас у еды **нет таймера** и `MOVE_SPEED` меняется постоянно; нельзя выдавать это за готовый «бафф на 20 секунд».

**M3 — пространственные слои/2D-мосты:** отделить `WorldPosition` от `Node3D`; реализовать типы мостов I/II/III, `DIRECT_GAZE`, `CAMERA_VIEW`, `CAMERA_FIXED`, камеру-зеркало и сохранение состояния. Переходы сначала на пустых комнатах.

**M4 — бой и spellcraft:** единый `HitEvent`, `DamagePipeline`, `AbilityRuntime`, физические снаряды и статусные реакции, комбо-контроллер, внятное AI, разные небоевые способы решения.

**M5 — sandbox story tests:** U-00…U-20 в data-first PuzzleDefinition, проверки альтернатив, раннего доступа, мягкого возврата, независимости от завершённых квестов. Постановку диалогов делать поверх этих систем.

**M6 — только после объективной готовности ассетов:** реальный 2D-мир, анимации, обжитые интерьеры, природные существа и катсцены. Никакие финальные персонажи и карты не требуются для M1–M5.
