## Принцип предметной системы

У любого переносимого объекта остаётся обычная **Entity с постоянным ID**. Его параметры, роль, теги, способности, исходная категория и магическое состояние не меняются, если игрок положил его в рюкзак. Оживлённый холодильник теоретически может быть переносимым; перенос запрещает его физическую симуляцию и скрывает визуальный Node, но не удаляет Entity из WorldRegistry.

Новый `InventoryService` манипулирует ссылками на сущности посредством компонентов `PICKUP` и `INVENTORY` и команд `CommandProcessor.execute_component`.

### Компоненты

- `PICKUP`: `enabled: bool`, `holder_id: EntityID | ""`, `weight: float`, `world_position: [x,y,z]`. Последние координаты сохраняются для восстановления после Undo. Параметр `holder_id` — единственный источник истины о владельце. Отдельных копий объектов в таблице инвентаря нет.
- `INVENTORY`: `max_slots: 1..24`, `max_weight: 0.5..200`. Подходит для любого HackableEntity, например холодильника-торговца. У Луны как игрока пока временные системные лимиты: 12 объектов / 50 единиц массы. Позже они будут привязаны к PlayerAvatar/Inventory компоненту.
- `ABILITY_SET` (из 0.25): объект продолжает носить собственные способности, даже находясь у другого существа.

Типы и пределы проверяются в `ComponentRegistry`; сторонний код или произвольные поля не исполняются. Списки принадлежащих объектов вычисляются из текущих Entity ID, поэтому не возникает дублирующихся записей «рюкзак vs мир».

### Операции

| API | Действие |
| --- | --- |
| `make_pickup(id, weight)` | Добавить переносимость действующей Entity |
| `add_inventory(owner, slots, max_weight)` | Дать существу место для предметов |
| `pickup(owner, item)` | Проверить дистанцию, доступность, число слотов, массу и отсутствие вложенного цикла; назначить владельца |
| `transfer(from, to, item)` | Передать объект другому контейнеру или Луне |
| `drop(owner, item, position)` | Вернуть в мир с координатами и коллизиями |
| `use(owner, item, ability, target)` | Использовать собственную способность переносимого объекта через `AbilityService` и `EffectEngine` |
| `list_items(owner)` | Получить отсортированные ID предметов указанного владельца |
| `sync_item / sync_all` | Привести физическое отображение объектов к их компонентам после команды, Undo или загрузки |

Во время хранения сущность невидима и не участвует в физике. Однако её данные и ID доступны для редактора, команд и будущих сценарных систем. Физический поиск по радиусу, атаки по области и AI-сенсоры не выбирают упакованный объект как будто он всё ещё лежит на земле.

Копия переносимого предмета при `COPY` или заклинании `COPY_ENTITY` появляется в мире **с пустым владельцем**, а не создаёт бесплатный второй предмет в чужом инвентаре.

Контейнер нельзя удалить, пока внутри есть другие реальные Entity: это предотвращает потерю содержимого и разрывы ссылок. Сам предмет можно удалить и восстановить по Undo; если в его данных был владелец, он возвращается к нему.

### Авторство и отмена

Передача, подбор и выбрасывание обновляют `PICKUP` через CommandProcessor, так что Undo/Redo может возвращать владельца, отображение и последнюю позицию в мире. `item.picked_up`, `item.transferred`, `item.dropped`, `item.used` поступают через EventBus и доступны правилам.

Использование предмета запускает способность с **позиции владельца**, хотя скрытый Node предмета остаётся на последней физической позиции. Audit содержит инициатора-владельца и источник `ability:ID@item_entity_id`. Проверка cooldown, дальности и применения эффекта остаётся общей для всех существ.

### Безопасность сохранений

`SaveService.apply_snapshot` теперь перед фазой создания/изменения делает **резервную копию текущего runtime-состояния**: позиций, параметров, ролей, тегов, компонентов Entity, позиции игрока, отношений, стихийных статусов, полей поверхностей, социальных состояний, правил и tombstones.

- Сначала проверяются все известные данные снимка, включая ссылки `PICKUP.holder_id`, вместимость владельцев и циклы вложенных контейнеров.
- Затем выполняются спавны, установка полей, восстановление сервисов и удаление объектов.
- При отказе фабрики, сеттера, импортёра или удаления система пытается **откатить уже изменённые объекты** к резервной копии, убрать вновь созданные Node и восстановить ранее удалённые. При невозможности полного отката возвращается подробная ошибка с `ROLLBACK INCOMPLETE`, а не ложный «МИР ЗАГРУЖЕН».
- После загрузки или отката `Main` синхронизирует видимость и коллизии переносимых объектов. Старые JSON-сохранения без `PICKUP` / `INVENTORY` остаются действительными.

**Ограничение:** необычная внешняя фабрика или setter, который отказывается принимать даже *прежнее корректное значение*, способен сделать восстановление неполным. Следующая ступень — настоящая `WorldSnapshotTransaction` с отделением фазы подготовки от любых эффектов и отказоустойчивым откатом. Гарантии внешних пользовательских скриптов пока отсутствуют.

### Проверки

- `test_save_rollback.gd`: искусственный отказ setter после частичного изменения, отказ удаления после первого удалённого объекта, восстановление прежних параметров и ID.
- `test_inventory.gd`: подбор, масса/владелец, передача, защита от рекурсивного вложения, запрет удаления заполненного контейнера, копирование переносимого, применение способности из рюкзака, выбрасывание, Undo/Redo и проверка целостности сохранения.
- В CI продолжают выполняться тесты старого World/Entity/Spell/Rule/Ability API.

## Следующие зависимости

1. Каталог предметных определений с безопасной сериализацией, уникальными ID и возможностью появления физических Entity из шаблонов.
2. **Используемые порции / еда / напитки:** операции `CONSUME`, долговременные эффекты, единая атомарная транзакция использования эффекта и списания порции. Пока базовый `use` не расходует предмет сам по себе.
3. Доставка предметов между мирами и забегами; `WorldManager` должен контролировать ссылки и адреса, чтобы содержимое инвентаря не терялось при переходах.
4. UI рюкзака и инвентаря существ, визуальная анимация поднятия и броска, адаптация физики и аур.
5. Обобщение команд и правил для нескольких lifecycle операций одновременно; предметные трансферы должны оставаться безопасными внутри сложных заклинаний.

До этого момента не считать визуальные инвентарь-слоты, готовую еду, артефакты или перенос между мирами реализованными.
