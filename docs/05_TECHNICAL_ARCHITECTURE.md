# 05 — Техническая архитектура, контракты и план реализации

**Статус:** проектная архитектура; **в репозитории пока только документация, не готовая игра**.  
**Основная платформа:** macOS; Godot 4 + GDScript — предварительно выбранный практический вариант.  
**Графика:** стилизованное 3D, ортографическая камера, 2.5D-ощущение, toon/shader outline, примитивы на старте.  
**Главный принцип:** игровая логика должна работать без финальных ассетов и, где возможно, без 3D-сцены.

## 1. Уровни проекта

1. **Definitions:** неизменяемые определения объектов, параметров, эффектов, способностей, артефактов, типов гравировок и сценариев.
2. **Runtime model:** отдельные экземпляры Entity, значения их параметров и текущие состояния.
3. **Simulation:** команды, эффекты, правила, способности, поведение, время, события, перемещения, сохранения.
4. **Presentation:** 3D-представление, HUD, редактор, звуки, каменные карточки, глитч.
5. **Meta simulation:** взаимодействия с HUD/границами, адреса карт, оконная оболочка, нестабильность и пустота.

Не позволять модели/кнопке UI становиться единственным источником игрового состояния.

## 2. Таксономия данных

### EntityDefinition — шаблон

Поля: definition_id, category_id, subcategory_id, default_roles, default_tags, component_spec, default_parameters, starting_abilities, model_key, icon_key.

**Определения не мутируются при редактировании экземпляра.**

### EntityInstance / EntityRecord

Поля: instance_id, definition_id, scenario_id, roles, tags, component_set, parameter_overrides, runtime_state, abilities, rules, relationships, inventory, transform, change_history.

Ссылки между объектами только по стабильным instance_id или сохранённым ссылочным идентификаторам. При удалении объекта все зависимости корректно обрабатываются; не хранить долговременные прямые указатели на временные Godot Node.

### ParameterDefinition

Поля: id, label_key, description_key, value_type, default, limits, ui_tab, ui_control, applicable_components, dependencies, advanced, icon_key, save_version.

Типы: bool, int, float, string, enum, color, Vector2/3 как типизированные структуры, entity_ref, definition_ref, tags, arrays, effect_list и т. п. Точные сериализационные схемы фиксировать перед реализацией.

**Текущие состояния отдельно от параметров определения:** state.health и state.energy могут меняться каждую секунду, не записывая каждый тик в Undo.

### Modifier

Для эффектов временного ускорения и аур: parameter_id, operation (set/add/multiply/clamp), value, source, priority, expires_at/condition. Система рассчитывает итоговое значение, сохраняя исходное. Для boolean/enum — приоритетная замена, для чисел — определённый порядок применения.

### SpellDefinition

ID, имя, триггер, способ доставки, target selector, effects, conditions, параметры силы/дальности/длительности, доступность/источник, **SpellCardAppearance** отдельно. Варианты карточек UI и кодовый режим должны управлять одной структурой.

### SpellCardAppearance

stone_color, stone_material, engraving_source (catalog/custom), engraving_id или strokes, line_width, bevel_depth, glow settings; без влияния на реальный урон/эффекты.

## 4. Контракт команды

Пример **схемы, не фактический готовый API**:

~~~json
{
  "operation": "parameter.set",
  "initiator_id": "player:luna",
  "source_id": "wand:luna",
  "target_selector": { "kind": "entity", "id": "tree_001" },
  "parameter_id": "visual.primary_color",
  "value": "#FF66CC",
  "transaction_id": "txn_001"
}
~~~

Выполнение:
1. Проверить тип и формат команды.
2. Разрешить цель.
3. Проверить права/совместимость и бюджеты.
4. Подготовить целостное изменение.
5. Применить его.
6. Сохранить инверсию/снимок для Undo при необходимости.
7. Записать **ChangeProvenance**.
8. Сформировать события.
9. Уведомить отображение и UI.

**Обязательное различие:** действия игрока и дискретные игровые эффекты — команды; непрерывная физика/движение — частые обновления состояния без накопления миллионов Undo.

Пример записи provenance: actor_id, source_id, scenario_id, command_id, affected_entity_ids, timestamp/tick, old/new_values summary, parent_event_id, origin (player/yuki/AI/rule/spell).

## 5. Контракт события и правила

~~~json
{
  "event_type": "combat.damage_received",
  "event_id": "evt_028",
  "initiator_id": "mushroom_1",
  "source_id": "projectile_2",
  "target_id": "tree_3",
  "root_event_id": "evt_001",
  "depth": 3,
  "payload": { "damage": 5 }
}
~~~

**RuleDefinition** = trigger + conditions (AND/OR/NOT) + target selector + effects + cooldown/priority/repeat_limit. Любой эффект должен работать от заклинания, предмета, еды, ловушки и правила без создания пяти отдельных систем.

**Безопасность:** события добавляются в очередь; для одной причинной цепочки — лимит глубины, количества операций за кадр, объектов-спавнов и повтора правила. При перегрузке — приостановить конкретную цепочку и показать диагностический глитч. Основной процесс не должен зависать.

**Нестабильность мира:** отдельный **геймплейный** счётчик, отражающий сложность/аномалии/конфликты; не мерить реальный FPS как условие разрушения. Редкие перегрузки могут открыть NullSpace.

## 6. Физика и представление

- StaticBody3D или инстансированная декоративная геометрия для множества обычных деревьев.
- CharacterBody3D/управляемые контроллеры для Луны/существ.
- RigidBody3D для динамических предметов с реальной физикой.
- Area3D для аур, водных участков, порталов и триггеров.
- Адаптер PhysicsAdapter согласует переключение физических режимов; не предполагать, что достаточно сменить bool у любого тела.
- VisualAssembler заменяет placeholder на реальный ассет по model_key, применяет цвета/материалы/масштаб/части; логика не привязана к модели.
- Простая геометрия: дерево = цилиндр + крона, гриб = шляпка + ножка, холодильник = коробка. Сложные формы позже.
- Проверять ортографическую камеру и рендер Godot Mobile/Compatibility на **конкретном Mac**, не обещать эффективность заранее.
- Возможны Sprite3D/рисованные лица, но основная модель событий/параметров остаётся 3D-совместимой.

### UI, мета-секреты и macOS

- Основные HUD/игровые окна управляются Godot, чтобы их состояния могли иметь связанный игровой ID.
- Физический доступ к HUD через край карты — **отдельный игровой режим взаимодействия**, а не взлом GUI каждым кликом везде.
- На macOS настоящая рамка окна контролируется системой; сцену «взлома заголовка» реализовывать средствами Godot в области приложения/специальной имитации, с проверкой режимов окна.
- Полноэкранный режим не должен препятствовать обычной игре.
- Мета-операции не изменяют реальные настройки ОС, файлы пользователя, разрешения системы.

## 7. Сохранения и реиграбельность

Разделить минимум на:
- **PlayerProfile:** исследовательский журнал, известные существа/формы, секреты, постоянные перки и достижения.
- **RunState:** текущая аркада, найденные артефакты, временные разблокировки, текущие конфигурации магии.
- **ScenarioState:** состояние/изменения конкретного мира.
- **RecoverySnapshots:** точки безопасного отката.

**Знания игрока не проверяются только по открытию записи.** Если правильное взаимодействие возможно в исходной симуляции, оно работает без записи в журнале.

Версия схемы и миграции обязательны. Использовать проверку сохранений/резервные копии. Удаление Луны, удаление сценария и перегрузка не должны повреждать PlayerProfile.

## 8. Порядок разработки

### P0 — минимальный Godot-проект
project.godot, main.tscn, GDScript, фиктивная сцена, smoke test, GitHub.

### P1 — чистое ядро данных
EntityDefinition, EntityRegistry, ParameterRegistry/Service, сериализация типов, тесты.

### P2 — команды, события и provenance
CommandProcessor, Undo, EventDispatcher, события изменения параметров, регрессия циклов.

### P3 — демонстрация мира
Луна ходит, ортографическая камера; дерево/гриб/камень/холодильник представлены простыми фигурами; выбор объекта, редактор параметров, изменение цвета/размера/физики.

### P4 — оживление и отношения
Жизнь, простое поведение, поиск целей, союзники/враги, лояльность Луне, базовая атака.

### P5 — эффекты, магия и правила
EffectEngine, AbilityService, карточный редактор заклинаний, применение эффекта, конструктор «Когда → Если → Сделать → С кем», возможность записать взлом как заклинание (после уточнения UX). Базовый каталог гравировок с placeholder.

### P6 — сохранения
PlayerProfile + RunState + ScenarioState; загрузка, Undo/Redo, клонирование, библиотека шаблонов, миграции.

### P7 — миры и глубокие системы
Карта/порталы, комедийные NPC, Юки как второй источник изменений, перки, каталог форм, подмена аватара, культы, лаборатория, социальная механика.

### P8 — мета и визуал
Переход к HUD у края карты, интерактивная рамка в оконном режиме, виртуальная нестабильность/пустота/запретные секции, финальные 3D-модели, каменные плитки с настоящими рисунками, эффект остановки мира.

**Не делать всю игру одной задачей.** Каждый этап должен иметь работающую точку проверки.

## 10. Контрольный вертикальный срез

Луна выбирает дерево → меняет цвет и размер → оживляет → даёт полёт → скрывает крылья → назначает грибы врагами → добавляет правило роста при касании → клонирует → удаляет оригинал → отменяет удаление → сохраняет → загружает.

Должны сохраниться: категории, роли, HP, способности, отношения, правила, визуальные параметры и ссылки. Другие деревья того же шаблона неизменны.

## 11. Как делить работу между чатом и агентами

**Из чата/через GitHub:** схемы данных, определения, сервисы, эффекты, команды, очереди, правила, сохраняемые структуры, unit/smoke-тесты, простые сцены и UI.

**Агент с графическим окружением:** сложная интеграция Godot/Blender, импорт ассетов, физика/навигация, визуальные эффекты, персонажные анимации, профилирование.

**Облако:** пакетная обработка текстур/моделей, тестовые сборки при доступном окружении. Наличие Godot или macOS-инстанса в облаке не гарантируется.

**Никогда не считать тест пройденным без фактического запуска.** Отсутствие графического доступа должно быть отмечено честно.

## 12. Требования к агенту, который продолжает разработку

1. Прочитать README и все docs, особенно [решения](06_DECISIONS_AND_OPEN_QUESTIONS.md).
2. Уточнить конкретный этап, не пытаться построить полную игру за один запрос.
3. Проверить существующие файлы и тесты до правок.
4. Не создавать вторую параллельную систему параметров/эффектов/сохранений.
5. Не менять семантику исходных категорий при оживлении.
6. Не привязывать способности к отображаемым крыльям/ртам.
7. Все системные изменения записывать с автором/источником ради Юки.
8. Не вводить чит-комбинации как основное открытие мета-возможностей.
9. Не превращать карточный редактор заклинаний в обязательную рунную грамматику.
10. Добавлять проверку и документировать реализованное отдельно от проектного.
