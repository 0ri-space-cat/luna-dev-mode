# Программируемые расходники — утверждённый принцип, рабочий технический контракт 27.11.2026

**Статус: [АВТОР §08.29]** Код после DEVELOPER, полностью зеркальные вкладки и редактируемые эффекты расходников утверждены. Точный язык, каталог эффектов и интеграция остаются [РАБОЧИМИ]; не отчёт о реализации. Источники: единый мануал §03.6 (EDIBLE/PORTIONS), §03.10 (Ноутбук Юки, Древняя Консоль), §05.9 (15 элементов, 44 зелья, 56 формул; неисчерпаемая склянка), §08.28.

## Предпочтительный дизайн
- Обычный TAB по еде: существующие поля EDIBLE/PORTIONS, конкретные эффекты предмета и их настраиваемые аргументы (лечение, длительность, сила). Не выводить все неизвестные эффекты списком. У существа фиксированный набор совместимых полей и действующие способности; произвольная запись нового поля не добавляет поведения.
- Поздняя вкладка Код для расходников/текущего состава склянки, [АВТОР] после настоящего DEVELOPER. Вкладка видима без дополнительного флага после открытия прав; не отдельный тайник, не подсвечивать туториалом. Позднее знание — какие реальные операции и события существуют, через мир и чтение существующего кода. Не заставлять угадывать синтаксис вслепую.
- [АВТОР] Полная двусторонняя зеркальность: один профиль, один набор имён и значений, все редактируемые поля и допустимые действия имеют представление в обеих вкладках. Добавленное в коде известное совместимое действие автоматически появляется в параметрах, с доступной редактурой его длительности, силы и иных аргументов; изменение поля сразу сериализуется обратно в код. Удаление/отмена также зеркальны. Не принимать выражение, которое невозможно полностью представить в графической вкладке. Сложные пользовательские действия не уничтожать при переключении. Не превращать редактор в полный Ноутбук Юки: только ограниченный триггер применения/поглощения, действие, аргументы, target, длительность. Ноутбук остаётся программированием событий, маршрутов, реакций и мира; использовать совместимый внутренний язык/операции по фактическому проекту, не новый полноценный язык с произвольным исполнением.
- Примеры концепции, не утверждённые токены: ON_CONSUME → HEAL TARGET 20; TEMP_EFFECT TARGET FLIGHT 15. Пончик с лечением и полётом, хлеб со свечением, уменьшение, временная гравитация/скорость. Конкретные ключи/единицы после проверки текущего effect registry. Эффект полёта временный, не переносимый FLY из банка, аналогично алхимии/Штампу; ни копирование, ни поедание не создают конечных экземпляров.
- Склянка Мии по-прежнему неисчерпаема, Enter смешивает 1–3 элемента, E пьёт, удержание/отпускание бросает порцию. В интерфейсе Мии не показывать полный код и неизвестные рецепты. TAB физической склянки при доступе — текущий разрешённый профиль эффекта; базовый рецепт неизменен. Рабочая модель: override принадлежит экземпляру склянки и выбранному составу; новое смешивание возвращает исходную формулу, не переписывает таблицу рецептов, пользователь может сохранить допустимый профиль отдельно только если согласовано. Бросок фиксирует копию эффекта порции в момент броска, не меняется задним числом. Для поверхностных зелий сохранить разные допустимые цели/триггеры, не переносить всё механически на ON_CONSUME.
- Еда с реальными порциями расходуется атомарно при успешном применении; копии независимые и наследуют допустимый эффект по обычному закону. Не делать всю еду неисчерпаемой. Действие применяется к фактическому поглотителю, если он совместим, не всегда к главной Луне. Таймеры игрового времени, совместимость с паузой и временными эффектами; при истечении убрать только overlay, не откатить постоянные хаки. Безопасный возврат размера/коллизии по общему закону.
- Валидация: разрешённый whitelist операций, типы/диапазоны, конечное число действий, отсутствие рекурсии/циклов, произвольного кода, системных прав, записи в чужие ID, прямого GAME_FRAME/META_WHITE_VOID/дублирования модуля. Не запрещать интересные физические обходы по ID пазла. Ошибка понятна, не ломает действующий профиль; применение целиком после проверки. Временное GLOW, полёт и физика могут переиспользовать действующие эффекты; не вводить новые сущности ради UI. Избыточные допустимые изменения подпадают под общий overload, не безграничная запись в память.
- Не выдавать SPAWN, TELEPORT и весь словарь глобальной Консоли через редактор расходника. Игрок получает знания по миру, существующим программам и реальным полям; отдельный справочник/автоперевод рун отменён. У существ произвольные новые параметры не добавляются; скрипты Юки остаются отдельной действующей системой.

## Зеркальность, парсер и границы (автор §08.29)
- Единственный источник истины — типизированный профиль экземпляра/состава, не два редактируемых хранилища. [РАБОЧЕЕ] parse → validate → atomic commit → render UI + canonical code; редактирование графического поля меняет тот же профиль. Все принятые конструкции должны иметь графическое представление и стабильную обратную сериализацию. Не сохранять произвольный текст как исполняемую логику. Не терять порядок эффектов, если он семантически важен. Не менять значения при переходе между вкладками.
- Имена параметров/эффектов в обеих вкладках совпадают; пояснения могут быть локализованы, но не новый язык. Лишние пробелы, табуляция, пустые строки, отступы не влияют на результат (не разрывать сам токен); определить грамматику разделителей отдельно. Ошибка синтаксиса/несовместимость не применяет половину профиля и не удаляет последнее валидное состояние; подсказка указывает конкретную ошибку, не раскрывает весь словарь.
- Знание через мир: действительный профиль временного полёта у пыльцы фей, другого расходника или зелья позволяет перенести совместимый эффект и его аргументы в пончик. Не новый модуль, не бесконечный FLY, не произвольное создание сущности или права. Не придумывать новое поле только ради примера. Демонстрационные FLIGHT/FLIGHT_DURATION не утверждённые API; использовать единый фактический реестр эффекта.
- Существа: открытый произвольный код в текущем объёме не вводить. Общие поля, видовые/индивидуальные компоненты и совместимые способности имеют реальную функцию; скорость спавна — у реального спавнера, а не автоматически у каждого порождённого животного. Разные типы тела и ситуации не должны сводиться к одной формуле взлома. Параметр, постоянный модуль, временный эффект и видовая функция не взаимозаменяемы. Если будущая редактура кода существ будет рассмотрена, сначала отдельное авторское решение, защищённая схема, инвариант конечного банка и реальная польза. Сохранить скрипты Ноутбука Юки.
- [РАБОЧИЕ тесты] Roundtrip: параметры → код → параметры без потери данных, добавление известного эффекта → появляется поле длительности, изменение длительности → та же строка, удаление → исчезает с обеих сторон, изменение порций/силы → совпадает, форматирование пробелами/пустыми строками → эквивалентно, неизвестное поле → профиль неизменён, недопустимый target/модуль → отказ, копия расходника не копирует конечный FLY; временный эффект истекает без отмены постоянных хаков. Проверить до массового контента.

## Оставшиеся технические решения
1. [РЕШЕНО АВТОРОМ] Вкладка Код после DEVELOPER, без отдельного сюжетного флага. Осталось согласовать конкретную грамматику/типизированные поля и UX применения.
2. Можно ли сохранять/копировать профиль изменённого состава склянки при смене рецепта? Рекомендуется явный reset на новый рецепт, не скрытая перезапись формул.
3. Какие реальные разрешённые операции применимы к расходнику, какие события питья/попадания/поверхности, и какие эффекты совместимы? Не утверждать пример кода как API.
4. Сложные эффекты: правила наложения, максимальные длительности, прерывание, визуальная индикация, сохранение/загрузка. Тест на обычном пончике и одном существующем зелье; доказать атомарное расходование, копирование, независимость рецептов и банка, возврат временного состояния, действующие права и отсутствие обхода системной границы.

Предложение не изменяет текущий игровой код или утверждённый список алхимии.
