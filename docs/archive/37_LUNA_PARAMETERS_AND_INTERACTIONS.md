# LUNA: DEV MODE — Каталог параметров, компонентов и взаимодействий

**Приложение 37 к [сценарию игры](36_LUNA_DEV_MODE_GAME_SCENARIO.md), редакция V1 от 06.11.2026.**

> Этот файл — **закрытый каталог стандартных типов для сценарной версии 1.0**, а не обещание математически «всех возможных» комбинаций песочницы. Для каждой новой самостоятельной игровой системы требуется запись в этом каталоге и тест. **[КОД 0.27]** означает, что ключ найден в текущем репозитории; **[ПЛАН V1]** — предлагаемый контракт, который ещё нужно реализовать. Фактические интерфейсы и ограничения уточнять по GDScript; не подделывать ответы прототипа. Технические английские идентификаторы предлагаются стабильными и могут быть согласованно переименованы до начала реализации.

## A. Грамматика всей симуляции

1. **Entity** имеет уникальный стабильный ¤ENTITY_ID¤, неизменную исходную категорию (например, TREE, FRIDGE, SYNTH) и независимые роли (CREATURE, NPC, MONSTER, COMPANION), теги, компоненты, параметры и состояние.
2. **Команда** всегда имеет ¤ACTOR_ID¤/источник, цель, действие, валидированный аргумент, порядок применения и журнал provenance. Не модифицировать сцену в обход CommandProcessor, если изменение должно сохраняться/восстанавливаться.
3. **Доставка** отделена от **действия**: палочка вызывает ¤SET SCALE¤ непосредственно, консоль — командой, зелье — при контакте, эмот — через свою физическую способность. Один эффект должен иметь один backend-путь.
4. **Видимость ≠ существование:** ¤WorldTruth¤ Entity/коллизии/состояние/адреса/история независимы от ¤ObserverProfile¤. Включение любого режима изнанки меняет отображение, не перемещает мост и не создаёт гиганта.
5. **Нельзя сделать проект бесконечно тяжёлым.** Ограничения количества Entity, повторов, глубины триггеров, жидких зон, наблюдений и восстановления — обязательные части мира; виртуальная «перегрузка» не вызывает намеренный реальный лаг.
6. В UI технические поля и значения — EN CAPS; человекочитаемые hover-подсказки на выбранном языке. Вкладки показываются только тогда, когда поле действительно применимо к типу цели.

## B. Точно зарегистрированные параметры в коде Godot 0.27

Источник: ¤scripts/core/parameter_registry.gd¤. **В коде зарегистрированы ровно эти 12 общих полей.** Это не равно полной реализации нижеописанных систем и не подтверждает существование дверей/жидкостей/рутов.

| Кодовый ID | Метка UI | Тип и допустимое | Установленное значение | Семантика в V1 |
|---|---|---|---|---|
| ¤alive¤ | ¤IS_ALIVE¤ | bool | FALSE | объект живой или нет; само оживление не меняет исходную категорию |
| ¤ai_enabled¤ | ¤AI_ENABLED¤ | bool | TRUE | автономное поведение |
| ¤behavior_mode¤ | ¤BEHAVIOR_MODE¤ | enum: WANDER, IDLE, FOLLOW, CHASE, FLEE, AUTO | WANDER | основной поведенческий режим |
| ¤target_group¤ | ¤TARGET_GROUP¤ | enum: LUNA, ANY, TREE, FRIDGE | LUNA | прототипный набор селекторов целей |
| ¤luna_relation¤ | ¤LUNA_RELATION¤ | enum: NEUTRAL, FRIEND, HOSTILE, AFRAID | NEUTRAL | грубое отношение к Луне; полноценные направленные отношения хранятся отдельно |
| ¤sense_range¤ | ¤SENSE_RANGE¤ | float 2.0–25.0, шаг 0.5 | 12.0 | радиус восприятия AI |
| ¤follow_distance¤ | ¤FOLLOW_DISTANCE¤ | float 1.0–7.0, шаг 0.2 | 2.0 | предпочитаемое расстояние следования |
| ¤health¤ | ¤HEALTH¤ | int 1–200 | 100 | текущее значение в редакторе; «смерть» как системное событие отдельно |
| ¤speed¤ | ¤MOVE_SPEED¤ | float 0.0–5.0, шаг 0.1 | 2.0 | обычная скорость движения |
| ¤size¤ | ¤SCALE¤ | float 0.5–2.0, шаг 0.1 | 1.0 | прототипный масштаб, не «любые размеры» |
| ¤material¤ | ¤MATERIAL¤ | enum: WOOD, FABRIC, METAL, STONE, ICE, ARCANE | STONE | профиль материала; горение/проводимость |
| ¤color¤ | ¤BASE_COLOR¤ | Color, стартовая палитра LAVENDER, MINT, PINK, BLUE, PEACH, VIOLET | LAVENDER | внешний цвет |

**Важное ограничение:** разговорные примеры «уменьшить до 0.25» из старого дизайна **пока не укладываются в предел ¤SCALE >= 0.5¤**, закреплённый в текущем коде. При реализации расширить диапазон через миграцию схемы (предложение V1: 0.10–8.00 с дискретными безопасными коллизиями), а не просто присвоить 0.25 в сценарном скрипте. Числа более 200 HEALTH/более 5 MOVE_SPEED тоже требуют явного изменения спецификации.

## C. Уже зарегистрированные компоненты [КОД 0.27]

Источник: ¤scripts/core/component_registry.gd¤. Их поля остаются **компонентами**, не надо дублировать их в глобальном ParameterRegistry без чёткой необходимости.

| Компонент | Поля и значения текущего кода | Игровой смысл |
|---|---|---|
| ¤INTERACTION¤ | ¤enabled: bool=true¤, ¤verb: USE/TALK/OPEN/INSPECT¤, ¤reach: 0.5–8.0, default 2.5¤ | доступная интеракция |
| ¤INVENTORY¤ | ¤max_slots: 1–24, default 8¤, ¤max_weight: 0.5–200, default 30¤ | контейнер любого существа |
| ¤PICKUP¤ | ¤enabled: bool=true¤, ¤holder_id: entity_id | ""¤, ¤weight: 0.1–100, default 1.0¤, ¤world_position [x,y,z]¤ | переносимая Entity, не уничтожает её ID |
| ¤ABILITY_SET¤ | ¤ids¤ — массив не более 16 уникальных имён навыков, каждая до 64 символов | назначенные способности |
| ¤TRIGGER_ZONE¤ | ¤enabled: bool=true¤, ¤radius: 0.5–12, default 2.5¤, ¤watch_group: LUNA/ANY/TREE/FRIDGE/CREATURE¤ | событие входа/выхода |

**Существующие сервисы и границы (по коду 0.27):**
- ¤EffectEngine¤ понимает типизированные изменения и операции lifecycle ¤COPY_ENTITY / DELETE_ENTITY / CREATE_ENTITY¤. В правилах поддерживаются ¤SET / ADD / MULTIPLY / TOGGLE / SET_RELATION / COPY_ENTITY / DELETE_ENTITY¤.
- ¤RuleEngine¤ ограничивает общее число правил 64, действий в правиле 12, глубину условий 5, ветвления 8, каскады событий; определения не являются произвольными сохранёнными GDScript-скриптами.
- ¤AbilityService¤ поддерживает максимум 64 определений и 12 действий в одной способности; текущие значения/таймеры и права проверять по файлу.
- ¤ArcaneGrammar¤: создание ENERGY/OBJECT/CREATURE, форма ORB/SHARD/BOLT, элемент FIRE/FROST/STORM, поведение SEEK/STRAIGHT/WANDER/FOLLOW/CHASE/FLEE/IDLE, выпуск PROJECTILE/PLACE.
- ¤MaterialProfile¤: WOOD и FABRIC горят, METAL и ARCANE проводят, STONE/ICE негорючие в текущем наборе. Нельзя приписывать дереву вечный огонь или стеклу заранее существующий профиль, если такой не добавлен.
- ¤ElementalStatusService¤: BURN, CHILL, FROZEN, SHOCK; FIRE может растопить лёд, STORM воздействует на проводимые/соответствующие состояния; баланс и числа прототипные.
- ¤SurfaceFieldService¤: ограниченные текущие поля ICE, STEAM; **произвольные разливы зелий пока отсутствуют**. Код ограничивает количество полей/радиус/длительность.

## F. Универсальные операции и строгая композиция эффектов

### F1. Стандартные операции V1

**[КОД 0.27, в разных сервисах]:** SET, ADD, MULTIPLY, TOGGLE, SET_RELATION, COPY_ENTITY, DELETE_ENTITY, CREATE_ENTITY; компоненты/инвентарь назначаются через типизированные команды в существующем коде. **[ПЛАН V1]:** SET_STATUS/REMOVE_STATUS, SET_MODEL_PART, MOVE_ENTITY_SAFE, SPAWN_LIQUID_FIELD, APPLY_CONTACT_EFFECT, SET_DESTINATION, BEGIN_TRANSITION, RESTORE_LOCAL_SNAPSHOT, REGISTER_EVENT_TRACE, DISPLAY_OBSERVER_LAYER, SET_PLAYER_ROUTE_IF_UNLOCKED, SET_LOCATION_TARGET_AT_SYSTEM_EDGE, OPEN_APP_FRAME_AT_SYSTEM_TARGET, ACTIVATE_EMOT_FROM_INVENTORY.

**Запрет:** не пытаться сохранить или выполнять произвольный пользовательский GDScript/Lua как часть правила. Последовательности событий ограничены размером, списком операций, допустимыми типами и cooldown.

### F2. Приоритет при конфликте статусов и параметров

1. Необратимая в рамках текущего тика проверка **существования/права** цели (валидный ID, Entity alive/deleted, permission).
2. Изменение системной идентичности/маршрута только после полной валидации адреса.
3. Команда, меняющая базовое значение параметра (например, ¤SCALE¤), сохраняется как базовое.
4. Временные статусы накладывают **оверлей** поверх базового (например, уменьшить на 40% на 15 секунд); истечение эффекта не возвращает давно удалённую Entity и не отменяет честно сделанную правку базы.
5. Несколько статусных эффектов следуют правилам stack-mode; одинаковые источники по умолчанию REFRESH, а не мультипликативный разгон без предела.
6. Physics rebuild происходит атомарно/через безопасную точку; при проблеме (объект внутри стены) выполняется ближайший корректный якорь/отказ.
7. Поведенческий режим подчиняется жёсткому FROZEN/SLEEP, затем критическому FLEE/FEAR, затем FOLLOW/CHASE/WANDER. Отношения и внешний вид не отменяют автоматически этот порядок.
8. Изменение видимости никогда не перестраивает физическую коллизию и не исполняет Command.
9. Undo/Restore включает связанные данные (компоненты, роли, отношения, ауры, резидуальные эффекты), но не отменяет реальное изученное знание игрока.

### F4. Тесты недопустимых и граничных операций

- Unknown ¤DESTINATION_ID¤ ⇒ no transition, no crash, no mutation of map.
- Effect on deleted Entity ⇒ no-op/structured error; no revival unless отдельное restore.
- Changing MODEL_BLUEPRINT does **not** silently clone/copy/erase social relationships.
- COPY of unique Entity ⇒ новая ID и разрешённое, ограниченное состояние; исключить бесконечное создание 10^6 копий.
- Liquid field count > budget ⇒ отказ/слияние с похожим полем по объявленным правилам, не зависание.
- Trigger ON_TOUCH вызвал новый ON_TOUCH ⇒ bounded event root, consistent replay.
- Антимеметическая Entity скрыта рендером ⇒ не скрывать звуки/коллизию/физический след по умолчанию.
- Удивительная игровая ситуация с нулевыми руками персонажа ⇒ не softlock, работает внешняя помощь/специальный способ restore.
- OUTSIDE не вызывает реальные ОС-системные вызовы/пишет файлы за пределами сохранений.
- Сохранение после переадресации двери/перехода/жидкости/зелья/эмота может быть загружено с тем же физическим результатом.
- Контроль информации: прогресс мета-исследования не должен выдать первый сюжетный финал в стартовом меню до его открытия.
