## Зачем

Правило **WHEN → IF → DO → TARGET** — общий примитив мира. Оно связывает параметры, события, магию, двери, NPC и будущие мета-аномалии без отдельного скрипта «для дерева» или «для холодильника». Например: если холодильник увидел дерево, меняем цвет дерева; если существу становится больно, другая сущность меняет отношение; если дверь обнаруживает посетителя, запускает допустимую цепочку эффектов. Позднее правила смогут ставить и Луна, и Юки — атрибуция заложена в `author_id` и командный source `rule:<id>`.

## Схема (0.19)

```gdscript
{
    "id": "luna:tree_alarm",
    "owner_id": "fridge_001",
    "author_id": "luna",
    "event_type": "entity.target_acquired",
    "target": "EVENT_TARGET",
    "priority": 15,
    "cooldown_ms": 0,
    "repeat_limit": 5,
    "enabled": true,
    "where": {"all": [
        {"field": "payload.group", "op": "EQ", "value": "TREE"},
        {"not": {"field": "payload.friendly", "op": "EQ", "value": true}}
    ]},
    "effects": [
        {"operation": "SET", "parameter_id": "color", "value": Color("f49fc9")}
    ]
}
```

`where`: AND (`all`), OR (`any`), NOT (`not`), сравнения `EQ / NE / GT / GTE / LT / LTE` по простым значениям из `payload.*` и `event.type/source_id/target_id`. Условие `conditions: [{"field":"group","equals":"TREE"}]` из старых прототипов поддерживается и переводится в каноническое дерево.

`target` выбирает `EVENT_SOURCE`, `EVENT_TARGET` или `RULE_OWNER`, затем действия исполняются через существующий `EffectEngine.apply_batch` и общий `CommandProcessor`. Виды эффектов: `SET`, `ADD`, `MULTIPLY`, `TOGGLE`, `SET_RELATION`. Приоритеты обрабатываются в воспроизводимом порядке; равные сортируются по ID.

Не путать: `repeat_limit` задаёт число успешных запусков в текущем мире, `cooldown_ms` опирается на runtime-часы и после перезапуска не восстанавливается; `EventBus` независимо ограничивает глубину и объём причинной цепочки. Счётчики по root event ограничивают частые повторения одного правила в одной цепочке.

## Безопасность и сохранения

- Максимум 64 правила, до 12 эффектов у каждого; глубина `where` и количество ветвей ограничены. Условие не допускает произвольного выполнения GDScript/JS.
- Правила хранятся как данные, без Node-ссылок и исполняемого кода. Значения типа Color проходят типизированный JSON-формат.
- `SaveService` валидирует всю сериализованную книгу правил **до изменения сущностей**; повреждённые правила отклоняют загрузку целиком.
- Сохраняются определения и счётчики успешных срабатываний. Временные cooldown-метки сбрасываются, потому что монотонные часы между запусками не сопоставимы.
- Старые сохранения без `rules` читаются, оставляя встроенное демо-правило текущей сцены. Данные иных систем, включая созданные заклинанием сущности и копии деревьев, продолжают использовать прежнюю схему.
- Редактирование через API: `register_rule`, `replace_rule`, `remove_rule`, `get_rule`, `list_rule_ids`, `export_data`, `import_data`. Визуальный интерфейс пользовательских правил на следующем этапе, без обхода этого движка.

## Чего пока нет

- Интерфейса создания пользователем новой автоматизации из карточек; backend готов для него.
- Правил по касанию, входу в портал/зону, таймеру, использованию еды — эти типы событий должны вырабатываться конкретными системами мира.
- Фильтров по тегам/ролям/отношениям между произвольными участниками; пока доступны поля событий.
- Создания новых сущностей, телепортации и системных мета-операций как новых типов EffectEngine; каждый должен быть явной безопасной типизированной операцией, без привилегированного eval.
- Полной интеграции provenance Юки и экспорта всех команд, пока только author_id у правил и source_id у изменений.
- Управления правилами в отдельной песочнице, аркадном обучении и книгах мира.
