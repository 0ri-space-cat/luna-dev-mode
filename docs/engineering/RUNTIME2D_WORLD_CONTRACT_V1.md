# Runtime2D: контракт будущих карт, существ и метамеханик

**Инженерная спецификация PR #22.** Художественный источник: `docs/canon/20_V6_AUTHOR_ONLY_BIBLE.md` и более поздние утверждения в `25–27`. Этот документ описывает исключительно код и проверяемые точки расширения. Он не утверждает карту, пазлы, новых NPC, параметры отдельных видов или рецепты зелий.

## 1. Загрузка уровней из будущей авторской карты

Внешний пример: `data/runtime2d/DEV_LOCATIONS.json`. Это ДВЕ ТЕСТОВЫЕ КОМНАТЫ, не география Этернии. После готовности Sheets-карты автор/агент экспортирует аналогичный JSON:

```json
{
  "locations": [
    {
      "id": "APPROVED_LOCATION_ID",
      "scene": "res://scenes/authored/approved_location.tscn",
      "required_access": 0,
      "entries": {"entry": [0, 0], "other_door": [128, 64]}
    }
  ],
  "doors": [
    {"id": "APPROVED_DOOR_ID", "destination": "APPROVED_LOCATION_ID"}
  ]
}
```

Каталог также может содержать `entities` внутри каждой локации. Например:

```json
{
  "id": "APPROVED_ENTITY_ID",
  "category": "object",
  "label": "Авторское название",
  "position": [128, 64],
  "parameters": {"alive": true, "ai_enabled": true},
  "components": {"ABILITY_SET": {"ids": ["GLOW"]}}
}
```

Это **формат одного объекта** массива `entities`, не фактическая сущность и не утверждённый автором ID. `EntityBlueprint2D` проверяет ID, тип, длины, допустимость параметров, компонентов и способность до создания актёра. При невалидной записи переход отменяется, текущая сцена остаётся нетронутой. Повторное посещение не перезаписывает уже изменённую Entity. `retire_actor` удаляет доверенной системной командой объект из текущей симуляции, а `deleted_ids` в V2-сейве сохраняет факт удаления. Возврат в комнату не возрождает удалённого персонажа; корректный более ранний снимок может восстановить его. Правила пользовательской кнопки удаления ещё требуют отдельного разрешающего слоя.

В примере ID и путь демонстрируют формат, они **не зарегистрированы** в игре. `LocationRouter2D.load_catalog_json()` проверяет ID, реальные PackedScene, числовые координаты, точки появления, доступ и все двери. Внутри будущей сцены автор может разместить `Doorway2D` на собственных координатах, указать существующий ID двери и имя точки входа. В отличие от DEV-заглушек, произвольным уровням движок не подбрасывает технических дверей. Если хотя бы одна строка недопустима, старый каталог остаётся неизменным. `redirect_door()` действительно меняет адрес в таблице маршрутов, `resolve_door()` разрешает адрес и вход, а `WorldController2D._enter_location()` меняет сцену. Взлом названия локации и телепортация по ID через мини-карту отсутствуют.

Событие `location_entered(address)` отдаёт текущий ID будущему UI для отображения. Существа других комнат сохраняют собственные ID, параметры и положение, но не отрисовываются и не участвуют в физике активной комнаты. При возврате их состояние восстанавливается. Для крупных карт загрузку неактивных комнат следует перевести с спящих узлов на сериализованные чанки.

## 2. Геометрия и перспективный арт

`LevelShell2D` содержит разные узлы для:
- `RegisteredBackgroundPlates`: две **строго одинаковые по размеру и регистрации** текстуры обычного мира/голубой изнанки; смена влияет только на изображение;
- `AuthoredCollision/GameplayGeometry`: настоящая физика, не пиксели на фоне;
- `LocationEntities`: самостоятельные сущности/живые объекты;
- `AmbientEffects`: отдельные эффекты;
- `StaticForegroundOcclusion`: плоскость перекрытия спрайтов без игровой сущности.

`LevelGeometry2D` принимает данные вида `{"solids":[{"id":"WALL_ID","kind":"WALL","rect":[x,y,w,h]}],"zones":[{"id":"ZONE_ID","rect":[x,y,w,h]}]}`. В JSON используются координаты Godot 2D. Тип `WALL` имеет коллизию 1; низкие препятствия `GROUND_ONLY` имеют коллизию 4; участки `SWIM_REQUIRED` имеют коллизию 8, участки `CLIMB_REQUIRED` имеют коллизию 16; актёры на слое 2. `FLY` из `ABILITY_SET` позволяет пересекать низкие препятствия и водные участки; `SWIM` пересекает только водные участки. `CLIMB` пересекает только специально размеченные проходы, требующие лазания. Низкие препятствия без `FLY` остаются непроходимыми. **Настоящие стены и другие актёры сохраняют физическую коллизию независимо от способностей.** Правила глубины воды, анимации плавания, высоты полёта и посадки ещё не зафиксированы. Маркер `SWIM_REQUIRED` лишь техническая категория проходимости, фактические водоёмы появятся только после авторской карты.

Для уровня с разными перспективными ракурсами используется та же физическая система 2D. Перспектива 3/4 задаётся фоновой композицией, pivots и occlusion, но итоговая проекция и размер пикселя требуют тестирования на утверждённом арте. Полная физика лестниц/уступов ещё не реализована.

## 3. Общая Entity и способности

`ActorBody2D` использует `EntityRecord`, `ParameterRegistry`, `CommandProcessor`, `ABILITY_SET`, `WorldRegistry` из старого рабочего ядра. `MOVE_SPEED` меняет физическое движение, `SCALE` меняет радиус коллизии и визуального якоря, `IS_VISIBLE` прячет представление, сохраняя физическое тело. `IS_ALIVE` и `AI_ENABLED` включают базовое самостоятельное движение. `FLY`, `SWIM` и `CLIMB` работают через реальные компоненты и коллизии. `GLOW` создаёт самостоятельный PointLight2D, `REGENERATION` реально восстанавливает здоровье до текущего стандартного значения реестра с техническим периодом 2 секунды. Остальные способности из авторского списка не объявляются работающими, пока не появятся отдельные адаптеры и тесты. `BehaviorBrain2D` реализует IDLE, WANDER, FOLLOW, CHASE, FLEE и AUTO через живой 2D-поиск целей, дистанцию и отношение к Луне. Для преследования, следования и бегства он строит ограниченные маршруты через `GridNavigation2D` на основе Godot 4.3 `AStarGrid2D`, перепланирует путь при изменении карты, цели или способностей. Пять ограниченных навигационных сеток поддерживают землю, плавание, лазание, сочетание SWIM+CLIMB и полёт. `LocalAvoidance2D` добавляет локальное раздвижение траекторий при встрече самостоятельных существ, но пока нет глобальной кооперативной навигации, маршрутов по настоящим высотам и согласованной модели пассажиров. Видовые характеры, платформенные высоты, специальные движения и редактор маршрутов пока не реализованы. `AbilityBankService` из системного ядра переносит реальные способности между физически близкими Entity атомарно, с Undo/Redo.

`WorldController2D.register_visual(category, PackedScene)` принимает готовую 2D-сцену с реальным пиксель-артом и подключает её к `VisualAnchor` всех подходящих Entity; объекты не получают случайный визуал от других типов. Клоны получают отдельный `CharacterBody2D`, самостоятельный `EntityRecord` и тот же ресурс визуальной сцены через отдельный экземпляр. Подмена категорий, ассетов и физических данных не требует отдельного скрипта загадки.

`WorldRegistry.candidates_2d()` даёт детерминированный, ограниченный по количеству поиск сущностей с учётом группы, радиуса и активной комнаты. Кандидаты из другой комнаты и предметы в контейнере не попадают в локальную физическую выборку. Исторический `candidates(Vector3)` для 3D-совместимости не удалялся.

## 4. Наблюдение, камера и изнанка

`ProjectionField2D` хранит положение **и ID комнаты** оставленной палочки. С палочкой в кармане обычная картинка действует всегда, даже при другом ACTIVE TOOL. Только физически оставленная палочка + выход за радиус, в том числе уход в другую комнату, переключает обычный фон на изнанку. При возвращении в её радиус картинка снова обычная. Радиус в техническом тесте 320 px, ещё не канон.

`ObserverQuery2D` различает поле зрения камеры и локальный взгляд Луны (направление, дальность, закрытые глаза, тест на перекрытия статическими стенами). `ObservationBody2D` умеет быть всегда плотным, плотным при наблюдении либо без наблюдения, с источником `LUNA` или `CAMERA`. Это общий физический закон, а не готовый мост: авторские карты решат, где и как его использовать. `CameraFollowLock2D` имеет строго два режима: FOLLOW и LOCKED; объекты вне изображения текущей комнаты продолжают обновляться.

## 5. Игровые события, ограничения и сохранения

`EventBus` из старого ядра используется для очереди `gameplay_event` с ограничением **128 событий**, глубиной цепочки **6** и обработкой до **48 событий за кадр**. Зоны публикуют `ZONE_ENTERED / ZONE_EXITED`, общие изменения публикуют `PARAMETER_CHANGED / COMPONENT_CHANGED`. `WorldRuleEngine2D` уже принимает декларативные правила зон из каталога будущих уровней: оно может изменить обычный параметр живой Entity, адрес существующей двери или опубликовать авторское событие для последующей обработки. Поддерживаются `once`, лимит до 8 действий на событие и сохранение флагов `rule_flags` в V2. Никаких произвольных скриптов, исполнения кода, скрытых карт или готовых головоломок в движке нет. Впоследствии консоль Юки сможет интегрироваться с этим контрактом. Переполнение сообщает `integrity_notice` вместо настоящего краша. Количество сущностей ограничено 48 в текущем демонстрационном мире; это технический лимит прототипа, а не утверждённый баланс игры.

V2-сохранения лежат отдельно от 3D/V1 (другая версия формата). Запоминаются параметры, компоненты, ID, координаты и комнаты сущностей, адреса дверей, доступ палочки/Луны, палочка и её комната, положение и режим камеры, глаза Луны. JSON валидируется перед применением, в том числе при переходах между комнатами. Успешная загрузка очищает старые команды Undo и очередь событий, чтобы ссылки на удалённые Node не срабатывали после восстановления. Есть восемь ручных контрольных снимков и отдельно `WorldTimeline2D`: 64 автоматические секундные точки, ограниченный запрос возврата до 60 секунд, подтверждение успешного restore до фиксации отката и защитный таймер, который сам откат не снимает. Это техническая основа будущей Кнопки времени, **пока без игрового артефакта**, полной физической перемотки временных эффектов и точного авторского баланса. `WorldClock2D` поддерживает SLOW/NORMAL/FAST для движения, текущего AI и пассивного восстановления с временными коэффициентами 0.5/1/2; глобальная скорость интерфейса, ОС и защитного отката не меняется. Это пока адаптер нескольких систем, а не полный симулятор всех мировых явлений. `GameRecovery2D` хранит последний явно отмеченный безопасный снимок, при переполнении очереди сообщает через `recovery_available`, а `recover_last_safe_state()` выполняет полноценную загрузку существ, маршрутов, флагов, доступа, палочки и времени. Будущий UI нарисует кнопку отката; настоящее падение Godot и создание окон ОС для инсценировки сбоя не применяются. Межмировая симуляция и игровые спектакли сбоев всё ещё требуют отдельной художественной реализации.

## 6. Граница с интерфейсной командой

**Здесь нет HUD, мини-карты, редактора, наложенных подсказок или физического входа на интерфейс.** Будущая интерфейсная сцена отдельно подключается к событиям и методам WorldController2D. **Экран TAB должен вызывать `request_wand_parameter_edit`**, который проверяет переносимую палочку, расстояние, ту же локацию, обычность цели и защищённые поля. `set_entity_parameter` является доверенным API для авторских сценариев/тестов, его нельзя напрямую подключать к пользовательскому UI. Подключение `set_entity_ability`, смены доступа и HUD-параметров также потребует отдельной соответствующей политики, не следует открывать эти методы неограниченно. `register_visual`, сохранения и камера не создают собственных UI-элементов. Палочка использует будущий keymap E=заклинание, TAB=взлом; диагностические F-клавиши не являются конечным UI.

Физический HUD и взаимодействие с GAME_FRAME планируются позднее, после утверждённой UI-реализации. Режимы доступа PLAYFUL/DEVELOPER инструмента и отдельный ACCESS_LEVEL Луны уже представлены независимыми данными, но **права каждой будущей операции должны иметь свой сервер/игровой policy**: прямой вызов демонстрационного API без проверки не является итоговой безопасной системой взлома.

## 9. Формат декларативных реакций карты (пример, без реального секрета)

В элементе `locations[]` можно разместить поле `rules`, массив объектов такого вида:

```json
{
  "id": "APPROVED_RULE_ID",
  "event": "ZONE_ENTERED",
  "zone_id": "APPROVED_ZONE_ID",
  "actor_id": "luna",
  "once": true,
  "action": {
    "type": "SET_PARAMETER",
    "entity_id": "APPROVED_ENTITY_ID",
    "parameter_id": "is_visible",
    "value": true
  }
}
```

Идентификаторы в примере условные; **их нельзя считать утверждёнными секретами**. Допустимы события `ZONE_ENTERED` и `ZONE_EXITED`; действия `SET_PARAMETER`, `REDIRECT_DOOR`, `ANNOUNCE`. Правило обрабатывается только в своей активной комнате. Все события проходят через ограниченную очередь, одноразовые срабатывания сохраняются и перематываются, а ошибка в условии или параметре отклоняется без вызова произвольного кода. В будущем можно расширить типизированный набор условий для наблюдения и физических загадок после утверждения их содержания.

## 10. Динамическая геометрия наблюдения

`ObservationBody2D` может быть невидимым, всегда твёрдым или менять твёрдость в зависимости от **взгляда Луны** либо **игровой камеры**. Теперь `WorldController2D` синхронизирует текущие твёрдые тела этого типа с `GridNavigation2D.set_dynamic_walls()`: маршрут NPC реально перестраивается, если камера перестала видеть объект или Луна закрыла глаза. Когда препятствие исчезает, ранее преграждённый путь открывается. Размеры берутся из настоящего `physical_size` и мирового трансформа узла, включая его поворот; другая комната не наследует эти препятствия. Реконфигурация ограничена 32 такими стенами в локации, выполняется только при изменении набора или геометрии, а сверхлимитное состояние направляет сигнал восстановления. Точную художественную геометрию мостов и секретов утверждает автор.

`tests/test_runtime2d_dynamic_observation_nav.gd` проверяет реакцию на LOCKED-камеру, изменение коллизий и маршрутов, отказ от ошибочных Rect2 и разделение комнат.

## 11. Физический транспорт RIDEABLE

`rideable` является булевым параметром 2D Entity, по умолчанию выключенным. Доверенный игровой API `mount_actor(rider_id, carrier_id, offset)` разрешает посадку только рядом с настоящим существующим носителем в той же комнате, если у него есть RIDEABLE. Пассажир следует за движущейся Entity, не мешая коллизиями самому носителю. `dismount_actor(rider_id)` перебирает ограниченные близкие позиции и требует одновременно проходимой карты, отсутствия физических столкновений и свободной линии до высадки. Связь пассажира и носителя сохраняется в V2 и возвращается при перемотке, а повреждённые, циклические и межкомнатные ссылки отклоняются **до** замены мира. Клонирование пассажира не навязывает клону тот же транспорт.

Сейчас запрещены вложенные поездки, более четырёх пассажиров на носитель и переходы между локациями, пока Луна сидит верхом. Это технические ограничения против некорректной физики; дизайн транспорта, возможность управлять летающим скатом, место сиденья, анимации посадки и пересечение миров на транспорте будут уточняться после готового арта.

`tests/test_runtime2d_riding.gd` проверяет посадку, перемещение, восстановление, высадку, удаление носителя и отбраковку повреждённых ссылок. В `tests/test_runtime2d_world_laws.gd` дополнительно проверяется, что изменение способностей сущности вне активной комнаты не возвращает её коллизии.

## 12. P0 — обязательная проверка сцены и сохранения перед применением

Вход в любую сцену, основанную на `LevelShell2D`, теперь вызывает `preflight_geometry()` ещё до удаления прежнего уровня. Проверяются ограничения и синтаксис JSON (максимум 1 MiB), прямоугольники геометрии, реальные лимиты A*-сеток и тип сцены. Пустая сцена тоже создаёт рабочую навигацию. Если новый уровень некорректен, действующая сцена, её события и Actor остаются на прежнем месте. Каталог локаций отдельно ограничен 1 MiB, корректно отклоняет нефинитные координаты и нечисловые значения доступа.

`SaveStore2D` принимает только V2 JSON через `user://`, ограничивает файл 4 MiB, верифицирует временную запись, сохраняет прежнюю корректную версию в `.bak` и может восстановить её при повреждении основного файла. Искажённый JSON декодируется с сообщением об отказе, без искусственного engine ERROR. При восстановлении V2 проверяются ссылки пассажиров на носителей, ссылки переносимых предметов, существование комнат и координаты; удалённые ID остаются занятыми для новых клонов даже после рестарта. Резервная копия является последней **предыдущей** корректной записью, а не заменой игрового API `apply_snapshot` или гарантией сохранности произвольного устройства хранения.

`tests/test_runtime2d_storage_integrity.gd` проверяет невалидную геометрию сцены, неприменение повреждённого сейва, пустую карту, крупные и неверные JSON, восстановление `.bak`, отказ от нефинитных точек входа и защиту ID удалённых клонов.

## 13. P1 — физические предметы и толкание

`PICKUP` используется из общего `ComponentRegistry` без новой сущности инвентаря. `pick_up_entity(holder_id, target_id)` требует включённый компонент, физическую близость и одинаковую локацию, отказывает вложенным переноскам и ездящим пассажирам. Пока предмет несут, он остаётся полноценной Entity, следует за владельцем, не имеет физической коллизии и не попадает в обычный 2D-поиск ближайших целей. `drop_held_entity()` ищет свободный участок карты с проверкой физики, а `CommandProcessor` сохраняет переходы состояния и позволяет отменять/повторять взятие/высадку. `PICKUP.world_position` по исторической совместимости хранится как `[x,y,0]`, первые две координаты используются в 2D. При клонировании переносимого предмета новый экземпляр освобождается от прежнего владельца. В V2 сохраняются ссылки, а некорректные и циклические ссылки на переносчика отклоняются до восстановления. На текущем этапе один владелец несёт не более одного объекта; переход в другую комнату с предметом в руках запрещён до реализации межлокационного переноса вещей.

`pushable` является отдельно редактируемым булевым свойством Entity, по умолчанию выключенным. `push_entity(source_id, target_id, direction, distance_px)` проверяет принадлежность комнате, расстояние, направление, конечность чисел и допустимость предмета. Движение идёт через настоящий Godot `move_and_collide()`: объект не может телепортироваться через физическую стену. Результирующая позиция сохраняется и восстанавливается вместе с миром. **Поштучная Undo-команда именно для толчка ещё не реализована**, её нельзя выдавать за готовую. До неё возврат возможен через общий механизм контрольных точек и временной истории.

Всё перечисленное живёт в физическом игровом мире, а не в HUD. Интерфейс карманных комнат и взаимодействие с экранными полосками должны подключаться отдельно, когда другая команда закончит свои компоненты. `tests/test_runtime2d_physical_pickup.gd` и `tests/test_runtime2d_push.gd` проверяют перенос, независимость клонов, запрет неправильных ссылок, столкновения, безопасную высадку и сохранения.
